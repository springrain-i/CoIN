MoELoRA 向量化 Forward — 已实施

✓ optimize 分支
已在 optimize 分支实施向量化 LoRA forward
针对 moelora（CoINMOELoraLinear），将 8 次串行 Python dispatch 替换为 2 次 torch.einsum batched 操作。通过 COIN_USE_VECTORIZED_LORA 环境变量控制，默认启用，可随时关闭回退原始 loop。

原始 loop（8 次 Python dispatch，串行，无法 CUDA kernel 融合）：

# coinmoelora.py · 原始版本
for i in range(self.expert_num):  # 8 次串行
    result += (
        self.lora_B[active].loraB[i](
            self.lora_A[active].loraA[i](lora_x)
        )
        * self.scaling[active]
        * router[:,:,i].unsqueeze(-1)
    )

向量化版本（2 次 einsum，单次 CUDA kernel 融合所有专家）：

# coinmoelora.py · 向量化版本（optimize 分支）
# A_stack: (N, r_per, d_in)  B_stack: (N, d_out, r_per)
A = torch.stack([m.mlp.weight for m in loraA_modules], dim=0)
# (B,T,d_in) × (N,r_per,d_in)ᵀ → (B,T,N,r_per)
out_A = torch.einsum('bti,nri->btnr', lora_x, A)

B = torch.stack([m.mlp.weight for m in loraB_modules], dim=0)
# (B,T,N,r_per) × (N,d_out,r_per)ᵀ → (B,T,N,d_out)
out_B = torch.einsum('btnr,nor->btno', out_A, B)

# 加权求和：(B,T,N,d_out) * (B,T,N,1) → (B,T,d_out)
return (out_B * router.unsqueeze(-1)).sum(dim=2) * self.scaling[active]
使用方式
COIN_USE_VECTORIZED_LORA=1 python ...   # 默认启用
COIN_USE_VECTORIZED_LORA=0 python ...   # 回退 loop（用于 A/B 对比测试）

ZeRO-3 Bucket 尺寸调优 — 评估后跳过

⊘ 跳过

Bucket Size 是什么

ZeRO-3 将模型参数分片到各 GPU，每次 forward 必须先做 AllGather 把分散的参数片拼回来，用完再丢。AllGather 存在固定启动开销（NCCL kernel launch + PCIe 握手）， 与数据量无关。

Bucket 的作用是把多个小 tensor 攒成一大块再统一发送，减少 AllGather/ReduceScatter 的调用次数： 

# 无 bucket（默认极小）：每层单独发，224 次 NCCL 调用
AllGather(weight_q)  → AllGather(weight_k)  → AllGather(weight_v)  → ...

# 有 bucket（500MB）：攒满再发，几十次调用
AllGather(weight_q + weight_k + weight_v + ... 共 500MB)  → ...

对应两个配置项：allgather_bucket_size（forward 时收参数）和 reduce_bucket_size（backward 时归约梯度）。

为什么对我们的价值有限
  1. 显存余量不够：GPU 6/7 训练时已在 90%+（~21.6GB），剩余不足 2.4GB。 Bucket 是攒满才发的临时显存，200~500MB × 多层并发，很容易触碰 OOM。
  2. overlap_comm: true 已是更大的收益：通信与计算重叠是 ZeRO-3 最核心的优化， 已开启。Bucket size 只是在此之上减少 NCCL 调用次数，边际收益小。
  3. LoRA 训练通信量本就少：Backward ReduceScatter 只处理 LoRA adapter 梯度（rank×dim，远小于 7B）， 梯度通信本身不是瓶颈。
  4. 4 卡 PCIe 环境收益有限：Bucket 优化在几十卡 NVLink 集群效果显著（调用次数 × 卡数）。 4 卡 PCIe，单次 AllGather 启动开销可接受。
结论：跳过，不调整 zero3.json
风险（OOM）高于预期收益，且更高优先级的优化（向量化、批量推理）已完成。 若将来扩展到 NVLink 多机环境，可重新评估。

torch.compile Kernel Fusion — 评估后跳过

⊘ 跳过

torch.compile 是什么

PyTorch 2.0 引入的 JIT 编译器。第一次运行时把 Python 写的 forward 捕获为静态图，做两件事：

  • 消除 Python overhead：后续调用不再走 Python 解释器，绕过 GIL 和 dispatch
  • Kernel fusion：把相邻的小 kernel（einsum → scaling → sum）合并成 1-2 个大 kernel，减少显存带宽浪费

理论上对 MoELoRA forward 有收益：4 个独立 kernel（matmul A、matmul B、routing weight、scaling）可以 fuse。

为什么对我们的价值有限
  1. PyTorch 2.0.1 compile 不稳定：我们用的是 2.0.1，compile 初版。 遇到动态 shape、条件分支或外部 hook 时容易静默 fallback 到 eager 模式，等于没编译。 稳定可用需要 2.1+。
  2. ZeRO-3 hook 兼容性差：ZeRO-3 在参数上挂了 AllGather hook， torch.compile 捕获计算图时可能误处理这些 hook，需要 fullgraph=False 且大量调试，调试成本高。
  3. LoRA adapter 占训练步比例小：基础模型 forward（7B）才是计算大头， 只 compile adapter 部分收益有上限，实测估计 <5%。
  4. 首次编译开销大：每次 shape 变化重新编译，训练初期会阻塞几分钟。
结论：跳过，待升级 PyTorch 后重新评估
PyTorch 2.0.1 + ZeRO-3 的组合下，compile 的调试成本远超预期收益。 若将来升级到 PyTorch ≥ 2.2，compile 的稳定性和 ZeRO 兼容性均有大幅改善，届时值得重试。

ZeRO-2 可行性评估 — 不可行（已验证）

❌ 已排除

ZeRO-3 每次 forward 都要 AllGather 全部参数（7B × BF16 = 14GB）。 ZeRO-2 只 shard 梯度 + 优化器状态，参数不 shard，省掉 forward 时的 AllGather。

内存估算（LoRA 训练，梯度只来自 adapter 参数）：

项目ZeRO-3（当前）ZeRO-2（估算）
模型参数（BF16）~14GB 分 4 shard → 3.5GB/GPU14GB × 每 GPU
Gradient（BF16）分 4 shard分 4 shard
Optimizer（FP32，Adam）分 4 shard分 4 shard
Activation（grad ckpt ON）~2-4GB~2-4GB
总峰值估算/GPU~20GB ✓~22-23GB ⚠️
🔴 结论：ZeRO-2 不可行 — CPU RAM OOM（已实测，2026-05-29）

ZeRO-2 不做参数 offload，但本系统 DeepSpeedCPUAdam 仍需在 CPU RAM 保存优化器状态（FP32 Adam，28GB）。 实测：8 进程并发加载时 CPU RAM 需求 8 × 14GB = 112GB， 而可用 RAM 仅 83GB（系统 RAM 125GB 中 42GB 被 OS + 其他进程占用）， 进程被 OOM killer（SIGKILL -9）终止。

根因：ZeRO-2 将完整参数驻留在每个 GPU（24GB）+ CPU RAM 存优化器状态， 总 CPU 占用超出硬件限制。ZeRO-3 通过参数分片将每 GPU 的 CPU 占用降至 3.5GB， 才得以在 83GB RAM 环境下运行。

此结论在 4 卡（GPU 4,5,6,7）和 8 卡配置下均验证失败。ZeRO-2 优化方向正式排除。

Eval 加速 — Model Server 复用

📌 P3
当前 eval 流程
run_evals_T8.sh 对 8 个任务 顺序调用，每次都重新加载 7B 模型 + LoRA 权重（~30-60s 纯加载时间），8 个任务 = 4-8 分钟纯加载开销。

eval_common.sh 已经做了 GPU 级并行（每 GPU 一个 chunk），但没做 任务级复用：

# 现状：每个 eval task 都冷启动
for TASK in sqa textqa imagenet ...; do
    # 每次重新 load 7B + LoRA → GPU → run → exit
    python -m ETrain.Eval.LLaVA.CoIN.model_vqa_science \
        --model-path "$MODELPATH" ...
done

改法（渐进式）：

  • → 短期：把 8 个 eval 脚本合并为一个 Python 进程，按顺序切换 dataset，模型只 load 一次。改动小，收益稳定。
  • → 中期：用 vLLM 或 lmdeploy 起 inference server，eval 脚本改为发 HTTP 请求。吞吐量 5-10x 提升，支持连续 batching。
  • → 长期：SGLang（LLaVA 支持好）+ 多 GPU tensor parallel，全量 8 任务评估从小时级降到分钟级。
